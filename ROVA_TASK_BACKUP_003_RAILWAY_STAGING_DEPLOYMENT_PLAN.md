## 2. Worker architecture and resource budget

After separate authorization, use a **dedicated staging-only Railway service**, built from the repository root with `RAILWAY_DOCKERFILE_PATH=scripts/backup/Dockerfile`. The image installs the locked worker dependencies and PostgreSQL 18 clients; runs as UID 10001, not root; and has `ENTRYPOINT ["node", "scripts/backup/backup.mjs"]`. With no arguments it emits `idle_no_backup` and exits 0 without connecting; `--verify` validates configuration locally and exits. Leave the default start-command override empty. Do not reuse the web application's start or predeploy command. No HTTP listener, public domain, TCP proxy, inbound exposure, healthcheck, persistent volume, or application migration is needed. Do not keep an idle process alive; confirm Railway supports a non-restarting exited service and a separately invoked one-shot before proceeding.

Private staging PostgreSQL -> version check -> compressed custom `pg_dump` in private temporary storage -> AES-256-GCM client-side encrypted file -> conditional create in HTTPS R2 staging bucket -> HEAD/metadata/size check and full download SHA-256 comparison -> success or nonzero failure. There is no automatic deletion. `pg_dump` takes a consistent logical snapshot while concurrent writes continue, but may take read locks and impose database load. Encryption occurs **after** the plaintext dump is written: there is temporary plaintext at rest, not a streaming-only solution. Files are in a mode-0700 temporary directory and removed in `finally` on normal completion/failure; forced termination, crash, platform snapshots and underlying block storage can defeat cleanup. No plaintext should be deliberately retained. Confirm ephemeral filesystem encryption, isolation, crash cleanup and lifecycle with Railway; if that guarantee is insufficient, **block deployment** until an approved mitigation is implemented and tested. File deletion alone is not secure erasure on SSDs or copy-on-write storage.

Start with a **proposed cap of 1 vCPU and 512 MiB** and one replica, subject to plan limits and measured peak usage. Compression at level 9 trades CPU for storage. Disk must accommodate the compressed plaintext dump plus encrypted file plus downloaded verification copy (approximately **3 x measured compressed dump size**, plus overhead and headroom); restore similarly needs encrypted and plaintext copies. Filesystem capacity/ephemeral disk and encryption are unverified. Size using a conservative source-size estimate and measured first run, monitor database load, memory, disk and duration; revise only with approval. The process returns 0 after all steps finish, or nonzero on failure. A verified uploaded object can remain even when a later step fails.

### Key recovery outside Railway

Before any real run, escrow the key **and** its ID in an independently controlled encrypted secrets vault outside Railway, with at least two authorized recovery custodians, documented break-glass access and offline recovery instructions. Store R2 recovery access separately, also outside Railway. Demonstrate recovery into an isolated drill environment without using Railway's variable store or revealing the key. If escrow, custodians or independent retrieval are not proven, recovery after a Railway outage is **unverified** and the first run is blocked. Losing the key makes its backups unrecoverable; changing the ID alone does not rotate the key.

Recovery checklist: [ ] vault is outside Railway and access-controlled; [ ] independent recovery copy of the exact 32-byte key and its unique ID exists **before** the first live run; [ ] two custodians and break-glass procedure are recorded; [ ] authorized custodian can inject both into an isolated process without displaying/exporting them into chat, logs or reports; [ ] old key/ID pairs and R2 access remain available for the lifetime of their backups; [ ] independent retrieval and a complete restoration are documented as pass/fail without secret values.

## 6. Isolated restoration drill - separately approved

1. Provision a disposable PostgreSQL instance on the same isolated restore host, bound only to loopback; a remote destination, including a private one, is refused. Do not use staging/production application credentials, public ingress, application routing, notification delivery or outbound integrations. Restrict access to designated operators. Match the source/client major or use an explicitly tested newer restore server, install required extensions, and create an empty `template0`-based database named `rova_restore_<unique-name>`. The script independently checks the connected database, user, server address and absence of user objects before reading the backup and again before restoring.
2. Retrieve R2 read-only credentials and the key matching the object's key ID from the independent escrow, not from Railway. In the isolated restore runner, inject `BACKUP_ENVIRONMENT=staging`, the R2 configuration, `BACKUP_OBJECT_KEY` from the safe record, `RESTORE_TARGET_MODE=isolated`, `RESTORE_TARGET_DATABASE_URL` for the loopback disposable instance, and `RESTORE_ISOLATED_CONFIRM=I_UNDERSTAND_THIS_IS_AN_EMPTY_LOCAL_DATABASE`. Override the image entrypoint to execute `node scripts/backup/restore.mjs` as non-root; never run the backup entrypoint accidentally. Keep temporary plaintext on encrypted ephemeral storage with capacity for both copies.
3. The restore script checks HEAD metadata, downloads the object, checks encrypted size and SHA-256, authenticates/decrypts AES-GCM, verifies plaintext SHA-256, validates the archive list, verifies the empty target again, then runs `pg_restore --exit-on-error --no-owner --no-privileges`. It never uses `--clean`; populated targets are rejected and conflicting objects fail the restore. Staging and production destinations are unsupported, with no live-restore override. Restore can execute code defined by source superusers: trust/review source and keep the target isolated. Require exit 0 and `restore_succeeded`; handle failures explicitly without publishing unreviewed logs.
4. Compare the restored schema (tables, columns, indexes, constraints, extensions and migration state) with a DBA-approved expected catalog for the actual source snapshot; do not run migrations. Verify table counts and representative records including binary fields where present. For exact counts/record comparison, coordinate a separately approved **write freeze** spanning source baseline capture and completion of the backup, or use another independently validated same-snapshot comparison method; a later live query can legitimately differ. If no comparable baseline exists, report counts and spot checks as plausibility checks, **not** exact integrity proof. Compare approved representative records privately on the trusted operator system, record only pass/fail and aggregate counts, and never export rows, raw SQL output, personal data or unsalted record hashes to reports.
5. Prove recoverability after worker restart by completing the backup process, then starting a **fresh separate restore process** with the independently recovered key and the same retained object, and successfully restoring into a fresh isolated target. Default backup entrypoint startup is inert; never repeat the explicitly authorized execution command without fresh approval. Record elapsed recovery time and success/failure only.
6. After verification, terminate the isolated runner and database, destroy their disposable encrypted storage and encryption keys through the provider's documented deletion/cryptographic-erasure process, including temporary files, snapshots, logs and volumes. Confirm cleanup with the infrastructure owner; ordinary `rm` or container deletion alone is not proof of secure erasure. Preserve the R2 backup object. Never attach restored data to the app or expose it through artifacts or logs.

First preserve the initial backup through a complete independent restoration.

Rotate by generating a new independent key and unique ID, escrow and test it first, update the worker only with approval, and retain every old key securely until all backups encrypted under it have expired and a final recovery check has passed. ## 8. Security and recovery limits

- The worker has access to all staging data. Control operator, service, bucket and log access; do not include secret values or customer/applicant content in alerts or reports. Structured errors can still contain provider messages: review/redact before sharing. R2 credentials can potentially overwrite/delete objects; assume compromise can affect backups unless a verified independent protection exists.
- A private network isolates routing, not database authorization or proof of separate storage. Validate source identity and permissions independently.
- Temporary plaintext is unavoidable in this implementation. Normal `finally` cleanup is not guaranteed on forced termination; require provider-verified encrypted ephemeral storage and disposal, adequate disk, no persistent volume or crash artifact collection.
- `pg_dump` protects one database at a snapshot, not cluster-global roles, tablespaces, ACLs, ownership, external files, settings or other services. Recovery requires separately documented configuration and extension dependencies. No database or application secrets are backed up by this workflow.
- Daily logical backups are **not PITR**: no WAL replay or arbitrary timestamp recovery; potential loss is since the last successful snapshot, normally up to about 24 hours plus delays/failures. Restore duration, exact RPO and RTO must be measured. Verify independent volume backups and PITR separately; do not claim they are enabled.

1. Database owner: verified staging version, distinct service/volume/data/credentials, private endpoint, dump privileges, schema/extension scope, source load and migration status; explicit no-migration decision.
2. Security and data owners: staging data handling, ephemeral storage safeguards, bucket-only permissions, enforceable preservation control, independent key escrow and private restore/secure destruction.
3. Infrastructure/billing owner: actual plan/cron eligibility, resource/disk limits, costs, alerting and ownership.
4. Release owner: approved immutable worker source/image, staging-only service creation and **one-time execution**, without web deployment, migrations or production changes.
5. Separate approvals after successful first run: isolated restoration drill, and only after passing it, daily automation and a proven minimum-recoverable retention mechanism.
